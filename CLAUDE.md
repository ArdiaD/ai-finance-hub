# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Two things published together from `docs/` via GitHub Pages at **fame-ai.org**:
1. **FAME landing page** (`docs/index.html`) — hand-authored project + team page.
2. **AI-&-Finance Paper Hub** (`docs/hub/`) — the static front-end for a curated
   corpus, generated by the `aifinhub` Python pipeline in `src/`.

The Python package discovers papers from public sources, lets a human curate them
via a dated Excel file, and republishes the approved set as `docs/hub/papers.json`.

## Setup & commands

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e .                 # core
pip install -e ".[llm]"          # + Anthropic (enrich, LLM re-rank, nicer LinkedIn drafts)
pip install -e ".[fame]"         # + sentence-transformers (FAME embedding scoring)
cp .env.example .env             # then add optional API keys (see below)
```

Everything is driven through one CLI — `python -m aifinhub <command>` (also installed
as the `aifinhub` script). There is **no test suite, linter, or build step**; the
"build" is `build-site`, and verification is running a command and inspecting the DB
or generated `docs/hub/papers.json`.

The whole cycle is two commands around a human review step:

```bash
python -m aifinhub weekly                       # fetch → polish → review-export
#   → edit the decision column in data/excel/<DATE>_hub_db.xlsx (yes | no | feature)
python -m aifinhub publish data/excel/<DATE>_hub_db.xlsx   # import → build-site → draft-post
#   → push docs/ via GitHub Desktop, then post linkedin/linkedin_<DATE>.md
```

`weekly` and `publish` (in `workflows.py`) are thin wrappers over the granular
commands defined in `__main__.py` — every step (`fetch`, `polish`, `build-site`,
`fame-score`, `import-pdfs`, `enrich`, `backfill-urls`, `relabel-sources`,
`fix-dates`, `retag`, `reject`, `stats`, …) can be run on its own. `stats` prints
status counts; use it as the quick health check.

### API keys (`.env`, all optional)

`ANTHROPIC_API_KEY` (LLM enrich / re-rank / LinkedIn), `SEMANTIC_SCHOLAR_KEY`
(rate-limit-free URL/date lookup), `CROSSREF_MAILTO`, `SERPAPI_KEY` (Google
Scholar source, off by default). The pipeline works with no keys — arXiv + RePEc
are the reliable backbone.

## Architecture

**Data flow:** `sources/*` → `fetch.py` (score + dedup + store) → SQLite
(`data/hub.db`, via `db.py`) → `review_xlsx.py` (export/import decisions) →
`export.py` + `site.py` (`build-site` → `docs/hub/papers.json` + HTML).

- **`models.py` — `Paper`** is the single normalized record every source returns.
  Its **`fingerprint`** (first 16 hex of a sha1) is the dedup key and SQLite primary
  key: derived from a strong identifier extracted from the URL (arXiv id / DOI / SSRN
  id) when available, otherwise from the normalized title. `canon_venue()` here is the
  one place venue names are collapsed to a canonical form ("SSRN", "arXiv") — keep
  source naming consistent through it.

- **`db.py` — `DB`** wraps SQLite and is the working source of truth. A paper's
  **`status`** (`pending` / `approved` / `rejected`) is its hub membership — there is
  **no file moving**; every PDF lives in `data/pdfs/library/` regardless. `_migrate()`
  adds columns on open, so it's safe to extend `SCHEMA` and add a matching entry there.

- **Sources** (`sources/__init__.py` `REGISTRY`): each plugin is a function
  `fetch(source_cfg, fetch_cfg) -> list[Paper]`. To add one, write the module, register
  it in `REGISTRY`, and add an `enabled:` block under `sources:` in `config.yaml`.
  `fetch.py` wraps every source in try/except so one breaking source can't fail the run.
  Use helpers in `sources/base.py` (`http_get`, `cutoff_date`, `parse_date`).

- **Dedup is two-layer:** exact fingerprint match, then a fuzzy title check
  (`fetch.py`, `rapidfuzz` `token_sort_ratio >= 92`) to catch preprint-vs-published
  duplicates that have different identifiers.

- **Relevance gate** (`relevance.py`, config `relevance`): a paper must match ≥1 `ai_term`
  AND ≥1 `finance_term`, then a keyword `score` must clear `min_score` to enter the inbox.
  Optional LLM re-rank when `use_llm: true`.

- **FAME scoring** (`fame.py`): pure **embedding similarity** (sentence-transformers
  `all-MiniLM-L6-v2`, local/offline) between each paper's title+abstract and the project
  summary in **`fame/FAME.md`**. Cosine is rescaled (`SIM_LO=0.32`, `SIM_HI=0.72`) to a
  **0–100 percent** `fame_score`; `FAME_THRESHOLD = 50` drives the `FAME · NN%` badge.
  NOTE: the `fame-score` CLI help still says "LLM-score 0-10" — that's stale; the
  implementation is embeddings on a 0–100 scale.

- **The review surface** (`review_xlsx.py`): `review-export` writes a dated full-DB
  snapshot `data/excel/<DATE>_hub_db.xlsx` with a `decision` column pre-filled from
  current status (`yes`/`feature`/`no`); `review-import` flips status/featured from it.
  This is both the human interface and the weekly archival record.

- **Site generation** (`export.py` → `site.py`): emits `docs/hub/papers.json` with a
  content-hash cache-buster and renders `docs/hub/index.html`. The site is fully
  client-side (search / theme+source+year filters / FAME sort) — no server.

- **PDF handling** (`pdfs.py`, `ingest_pdf.py`, `enrich.py`): imported/downloaded PDFs
  are renamed `name1_name2_name3_year.pdf` and kept **local-only, never committed**.
  `enrich` LLM-extracts metadata for thin PDFs lacking an embedded identifier.

`config.py` holds all path constants (`DATA_DIR`, `DB_PATH`, `DOCS_DIR`, …) and a
minimal `.env` loader that fills only unset/empty vars (never clobbers a real exported
value). `config.yaml` holds sources, relevance terms, and the theme taxonomy.

## Privacy — never commit these (all gitignored)

- `data/` — the DB, the entire PDF archive, and Excel snapshots.
- `fame/` — the grant proposal + `FAME.md` (contains private/funding detail).
- `team/` (repo root) — source `.docx` profiles that embed personal emails. Only the
  **resized JPEGs in `docs/team/`** are public.
- `_other/`, `linkedin/`.

When touching anything in those folders, keep the public/private split: photos and the
public corpus go to `docs/`; everything with personal data stays under the ignored paths.

## The team page (`docs/index.html`)

Team members live in an editable `TEAM` JS array near the bottom of the file
(`{group, name, title, bio, photo, link}`). To add one: extract the `.docx` from `team/`
(it's a zip — `word/document.xml` for text, `word/media/` for the photo), resize the
photo to a ~500px JPEG in `docs/team/` (`sips -s format jpeg -s formatOptions 80 -Z 500
in --out out.jpg`), and add an array entry. A missing/empty `photo` falls back to a
coloured-initials avatar; an empty `title` is omitted.
